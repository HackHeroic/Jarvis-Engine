 Jarvis Architecture Review, Gap Analysis & Roadmap

 Context

 Madhav asked for a comprehensive architectural verification: are we building the right thing, what triggers should cause
 replanning, what's missing, what to test, when to build the real frontend, and how DKT/RL fit in. This plan synthesizes findings
  from a deep codebase exploration, the research docs, the jarvis-demo frontend, and all 24 plan files.

 Verdict: The architecture is fundamentally sound. The Control Policy -> Socratic Chunker -> OR-Tools CP-SAT pipeline is
 well-designed. Multi-goal fusion, habit translation, horizon expansion, biological fallbacks — all correctly implemented. The
 major gap is the absence of a feedback loop — users can't mark tasks done, the system can't learn from completions, and nothing
 triggers replanning autonomously.

 B. Gap Analysis (Priority-Ordered)

 P0 — Primal (System doesn't work as a product without these)

 1. Task Completion Endpoint
 - Problem: No way for users to mark tasks done. No POST /api/v1/tasks/{task_id}/complete.
 - Impact: No feedback loop → no DKT input → no RL reward → no completion rate tracking → no rollover logic
 - Files: New app/api/v1/endpoints/tasks.py, mount in app/api/v1/router.py
 - Schema: TaskCompletionRequest(task_id, user_id, quality: 0-5, actual_duration_minutes)

 2. Task Mutation Endpoints
 - Problem: No PATCH/DELETE for individual tasks post-scheduling
 - Impact: Users can't edit duration, skip, delete, or reorder tasks
 - Files: Same tasks.py — PATCH, DELETE routes

 3. Internal Replan Trigger Function
 - Problem: After saving a constraint or ingesting a doc, system returns suggested_action: "replan" but waits for user to
 manually chat again
 - Impact: Every trigger except #1 is broken without this
 - Solution: async def trigger_replan(user_id: str, reason: str) in control_policy.py that calls _run_plan_day_flow with pending
 tasks
 - Not a new endpoint — reuses existing pipeline headlessly

 P1 — Important (Needed for autonomous behavior)

 4. In-Process Event Bus
 - NOT Redis/RabbitMQ. Simple asyncio event dispatcher inside FastAPI process.
 - File: New app/core/event_bus.py
 - Events: TASK_COMPLETED, CONSTRAINT_CHANGED, DOCUMENT_INGESTED, DEADLINE_UPDATED, REPLAN_REQUESTED
 - Publishers: orchestrator.py, behavioral_store.py, tasks.py
 - Handlers registered in app/main.py lifespan

 5. SSE Notification Channel
 - GET /api/v1/events/stream — persistent SSE connection for server-push
 - When background replan completes, push: {"type": "schedule_updated", "reason": "..."}
 - Frontend already parses SSE (jarvis-demo lib/api.ts)
 - File: New app/api/v1/endpoints/events.py

 6. Signals/Telemetry API
 - POST /api/v1/telemetry/signal — accept task completion, focus level, mood, time-tracking
 - Currently telemetry.py is a 1-line stub
 - Schema: Signal(type: str, value: float, task_id: Optional[str], timestamp: datetime)
 - This is the L1 Evaluation layer and the input pipeline for DKT/RL

 P2 — Nice-to-Have (Adds intelligence, system works without)

 7. Morning auto-plan cron — asyncio background task in lifespan, not external cron
 8. DKT implementation — After Signals API has 50+ completions per user
 9. RL implementation — After DKT provides mastery scores
 10. MCP integration — Slack/email/calendar webhooks
 11. SARIMAX live integration — After 2+ weeks of telemetry data

 C. Event-Driven Architecture: Assessment of Gemini's Suggestion

 Event Bus: YES, but in-process only

 Gemini is right that you need event-driven behavior. But you don't need Redis or RabbitMQ. The system runs on a single M4 Pro. A
  simple in-process event bus is the right tool:

 # app/core/event_bus.py
 class EventBus:
     _handlers: dict[str, list[Callable]] = defaultdict(list)

     def subscribe(self, event_type: str, handler: Callable): ...
     async def publish(self, event_type: str, payload: dict):
         for handler in self._handlers[event_type]:
             asyncio.create_task(handler(payload))  # fire-and-forget

 This pattern already exists in the codebase — asyncio.create_task is used for parallel search in control_policy.py. The event
 bus just decouples publishers from subscribers.

 WebSockets: NO, not now

 SSE is already working end-to-end (backend streams, frontend parses). WebSockets add bidirectional complexity not needed yet.
 The only server→client push needed is "your schedule was updated in the background" — SSE handles this perfectly. WebSockets
 justified only for real-time collaborative features (not on roadmap).

 Minimal viable background replanning flow:

 Service publishes REPLAN_REQUESTED(user_id, reason)
   → Event bus handler calls asyncio.create_task(trigger_replan(...))
     → _run_plan_day_flow runs with pending tasks (headless, no HTTP)
       → _persist_fused_tasks updates Supabase
         → SSE push: {"type": "schedule_updated", "reason": "..."}
           → Frontend shows toast + refreshes schedule

 E. Frontend Roadmap

 Keep jarvis-demo. Do NOT start a new frontend.

 jarvis-demo is functional Next.js 14 with SSE streaming, all the right pages, TypeScript types, and demo mode. Starting over
 wastes 2-4 weeks with zero value.

 Backend must prove these first (before frontend polish):

 1. PLAN_DAY confirm flow works reliably end-to-end
 2. Task completion mutates state correctly
 3. Multi-goal fusion works across sessions
 4. Background replan + notification push works

 Frontend priorities (in order):

 1. Task completion UI — "Done" button on each scheduled task → POST /tasks/{id}/complete
 2. Notification toast — When background replan completes, show "Schedule updated because [reason]"
 3. Schedule auto-refresh — After completion or notification, reload schedule
 4. Habit due indicators — Show which habits are due today (already has GET /habits/tracker/due)
 5. Task editing in confirm flow — Drag-to-reorder, duration adjust, remove tasks before confirming

 When to start the "real" frontend:

 After all 5 priorities above are validated AND DKT provides real mastery scores visible in UI. At that point, invest in design
 polish, Notion-like environments, MCP connections, mobile responsiveness. Estimate: 6-8 weeks from now.

 F. DKT + RL Integration Path

 DKT — Start after Signals API (P1)

 What DKT does: Tracks P(mastery | knowledge_component) over time via LSTM.

 Minimal viable integration:
 1. Data source: Task completion signals from Signals API → (user_id, KC_tag, quality, timestamp)
 2. KC_tag mapping: Task title → KC_tag via embedding similarity against ChromaDB topics (reuse existing Nomic embeddings)
 3. Model: Simple LSTM in dkt_lstm.py using PyTorch or MLX
 4. Integration point: DKT output overrides difficulty_weight in TaskChunk:
 difficulty_weight = 1.0 - P(mastery | KC)
 4. Low mastery = high weight = more time allocated by OR-Tools
 5. Cold start: Until 50+ completions per user, use LLM-assigned difficulty_weight. DKT fades in gradually.

 Implementation sequence:
 - Week 1-2: Signals API + KC taxonomy mapper
 - Week 3-4: LSTM implementation + training pipeline
 - Week 5: Wire into _run_plan_day_flow to override difficulty_weight

 RL — Wait until DKT works

 RL (DQN) depends on DKT mastery scores as state input. Without DKT, RL state would be (tasks_remaining, time_to_deadline) — a
 worse version of TMT which already works deterministically.

 When DKT is ready, RL integration:
 - State: (DKT_mastery_vector, tasks_remaining, time_to_deadline, energy_cycle, day_of_week)
 - Action: Priority ordering of tasks
 - Reward: +1 completed quality >= 3, -0.5 skipped, -1 deadline missed
 - Output: Replaces TMT priority weights in CP-SAT solver
 - Estimate: 4-6 weeks after DKT is validated
