Level 5 — Permission Pipeline (9 Steps)

1
Deny rules match? — Check alwaysDenyRules[source][] from 8 rule sources (userSettings, projectSettings, localSettings, flagSettings, policySettings, cliArg, command, session). If match → DENY.
2
Ask rules match? — Check alwaysAskRules[source][]. If match → ASK. Exception: Bash may auto-allow if sandboxed.
3
tool.checkPermissions(input) — Tool-specific permission logic (e.g., BashTool checks for dangerous commands). Returns allow/ask/deny/passthrough. (Corrected: was step 0, actually step 3)
4
Safety check — Protected paths (.git/, .claude/, .vscode/, shell configs). Bypass-immune — even bypassPermissions mode can't suppress. → ASK.
5
Mode-based allow? — If bypassPermissions mode → ALLOW.
6
Always-allow rules — Check alwaysAllowRules[source][]. If match → ALLOW. (Corrected: separated from mode-based allow)
7
YOLO Classifier (auto mode only, gated by TRANSCRIPT_CLASSIFIER) — Fast paths: safe tool allowlist (Read, Grep, Glob, Task tools) → instant ALLOW. Otherwise: API call to classifier with transcript + action. Returns shouldBlock + confidence. Denial tracking: after 5 consecutive blocks → fallback to prompting.
8
Permission hooks — Can override any previous decision. Hook result can set behavior to allow/deny/ask. (headless agents only)
9
Interactive prompt — If still ASK: show permission dialog to user. Coordinator workers: await automated checks first. Swarm workers: special handler. User can approve, deny, or modify input.

Level 6 — 4 Compaction Types

1. Micro-compact

When: Every iteration, before API call
What: Lightweight token reduction — shrink tool results, remove redundant whitespace
Cost: Zero API calls
Gate: CACHED_MICROCOMPACT
services/compact/microCompact.ts

2. Auto-compact

When: Token count ≥ contextWindow - 20K - 13K
What: Full summarization via forked API call. Preserves last 5 file reads, plan info, skills
Cost: 1 API call (forked model)
Breaker: 3 consecutive failures → stops
services/compact/autoCompact.ts

3. Snip-compact

When: Every iteration (gated HISTORY_SNIP)
What: Remove old messages by history boundary — no summarization, just cut
Cost: Zero API calls
Gate: HISTORY_SNIP feature flag
query.ts:401 → snipCompactIfNeeded

4. Reactive-compact

When: AFTER 413 prompt-too-long error
What: Emergency recovery — 3 stages: context collapse drain → full reactive compact → give up
Cost: 1+ API calls
Gate: REACTIVE_COMPACT
query.ts:1119-1166

Level 7 — Tool & Skill System

Tool (Tool.ts interface)

54 possible tools (19 unconditional + 35 feature-gated), each implements:
inputSchema (Zod) → exposed to LLM
call(args, ctx) → execution
checkPermissions(input, ctx) → allow/ask/deny
isConcurrencySafe(input) → parallel ok?
isReadOnly(input) → side-effect free?
maxResultSizeChars → disk if exceeded

StreamingToolExecutor:
Read-only tools (Grep, Glob, Read) run in parallel.
Mutating tools (Bash, Edit, Write) sequential.
Bash errors abort siblings; others don't.

Skill (SkillTool → Command)

Markdown files with YAML frontmatter
Sources: bundled, user, project, plugin, MCP

Lazy loading: only frontmatter at startup
Full content loaded on invocation

Two execution modes:
Inline: inject into current conversation
Fork: spawn sub-agent via runAgent()

Key frontmatter fields:
allowed-tools, model, context (fork|inline),
hooks, agent, effort, paths, arguments

Skills CAN invoke tools. Skills ARE invoked
via SkillTool (a meta-tool in the 54).

Level 9 — AsyncGenerator Streaming Architecture

The entire system uses AsyncGenerator<T> — not callbacks, not promises, not event emitters. This is an architectural choice that enables real-time streaming at every layer with backpressure.
// Layer 1: API → query loop
async function* queryModelWithStreaming(): AsyncGenerator<StreamEvent>

// Layer 2: query loop → QueryEngine
async function* query(): AsyncGenerator<Message | StreamEvent>

// Layer 3: QueryEngine → UI/SDK
async function* submitMessage(): AsyncGenerator<NormalizedMessage>

// Layer 4: Tool execution
async function* getRemainingResults(): AsyncGenerator<ToolResult | Progress>

// Layer 5: Stop hooks
async function* handleStopHooks(): AsyncGenerator<StopHookResult>

// Every layer yields → consumer pulls on demand → natural backpressure
// No buffering, no dropped messages, no callback hell

Corrections to Simplified Diagram

1. "Agent → Reasoning Loop" = QueryEngine.submitMessage() → query() → queryLoop() — 3 layers
2. Sub-agents call query() directly, NOT QueryEngine
3. Hooks are inside the loop wrapping each tool, not between Agent and Tools
4. Memory fires proactively at loop top, not reactively "when full"
5. Tools execute during streaming, not sequentially after
6. Sub-agent hooks are session-scoped by agentId, not inherited
7. Skills are a meta-tool (SkillTool) — not same as tools
8. Context = 4-tier chain (managed→user→project→local), not just "CLAUDE.md"
9. Memory recall uses Sonnet side-query, not embedding similarity
10. Stop hooks trigger memory extraction + auto-dream + prompt suggestion
11. 27 hook events (not just Pre/PostToolUse) across 6 categories
12. 89 feature gates via Bun DCE control which subsystems exist at build time
13. 9-step permission pipeline — deny rules FIRST, then ask, then tool.checkPermissions, safety, mode, allow rules, YOLO classifier, hooks, interactive
14. 4 compaction types (micro, auto, snip, reactive) — not just "auto-compacts"
15. Entire system uses AsyncGenerator for real-time streaming with backpressure
16. 54 possible tools (19 unconditional + 35 feature-gated), not 43
